# AgentGateway

## Install AgentGateway using Helm
We can follow the [installation instructions](https://agentgateway.dev/docs/kubernetes/latest/documentation/quickstart/install/)
<!-- Conceptual explanation of Helm -->

```bash
helm upgrade -i agentgateway oci://cr.agentgateway.dev/charts/agentgateway \
  --namespace agentgateway-system \
  --version v1.6.0 \
  --set controller.image.pullPolicy=Always \
  --wait
```

## First bug: a missing address

`kubectl get gateway agentgateway-proxy -n agentgateway-system ` shows no address
```
NAME                 CLASS          ADDRESS   PROGRAMMED   AGE
agentgateway-proxy   agentgateway             True         37h
```

`kubectl get svc -n agentgateway-system` shows

```
NAME                 TYPE           CLUSTER-IP      EXTERNAL-IP   PORT(S)                      AGE
agentgateway         ClusterIP      10.43.77.225    <none>        9978/TCP,9093/TCP,9092/TCP   37h
agentgateway-proxy   LoadBalancer   10.43.182.220   <pending>     80:32319/TCP                 36h
```

`kubectl describe svc agentgateway-proxy -n agentgateway-system` shows

```
 Type    Reason                Age   From                   Message
  ----    ------                ----  ----                   -------
  Normal  EnsuringLoadBalancer  11m   service-controller     Ensuring load balancer
  Normal  AppliedDaemonSet      11m   service-lb-controller  Applied LoadBalancer DaemonSet kube-system/svclb-agentgateway-proxy-ef8d7391
```

The problem is that the default AgentGateway manifest I applied creates a Service named `agentgateway-proxy` of type `LoadBalancer`, exposed on port 80. On default k3s, `LoadBalancer` Services are handled by the built-in ServiceLB, which forwards the Service's listening port directly on the node. Traefik, the default ingress controller in k3s, already claims port 80 and 443 on every node (via `svclb-traefik` pods created by ServiceLB). This port collision means the `svclb-agentgateway-proxy` pods can't bind to the node's port 80, so the scheduler leaves them in `Pending`. You can see the stuck Service pod by running:
```bash
kubectl get pods -n kube-system -l svccontroller.k3s.cattle.io/svcname=agentgateway-proxy
kubectl describe pod -n kube-system <svclb-agentgateway-proxy-####>  
```

```
Events:
  Type     Reason            Age                  From               Message
  ----     ------            ----                 ----               -------
  Warning  FailedScheduling  9h (x330 over 36h)   default-scheduler  0/1 nodes are available: 1 node(s) didn't have free ports for the requested pod ports. no new claims to deallocate, preemption: 0/1 nodes are available: 1 node(s) didn't have free ports for the requested pod ports.
  Warning  FailedScheduling  29m (x6 over 3h58m)  default-scheduler  0/1 nodes are available: 1 node(s) didn't have free ports for the requested pod ports. no new claims to deallocate, preemption: 0/1 nodes are available: 1 node(s) didn't have free ports for the requested pod ports.
```

Load balancers and traffic routing deserves its own article, which we will get to in the next one, but for now, just know that for each `LoadBalancer` Service, ServiceLB runs a `DaemonSet` of `svclb-*` pods that claim the Service's ports on every node and forwards the incoming traffic to the Service's ClusterIP.

## Second thing: Accessing the admin dashboard
Agentgateway comes with an admin dashboard that lives on port 15000. We can't reach this port through the service that we have. Instead, we can just port-forward for now. Later on, we'll see how to set this up with an actual private domain name. 
```bash
kubectl -n agentgateway-system get deploy agentgateway-proxy -o yaml # check the exact port that the dashboard is on
kubectl -n  agentgateway-system port-forward deploy/agentgateway-proxy 15000
```
